# Security

What the platform defends against today, how, and — just as importantly — what it does not yet
defend against. This document is written against Phase 1. Anything deferred to a later phase is
labelled as such rather than implied to be present.

## Scope and non-goals

The platform models card and account transactions. It deliberately does **not**:

- store a primary account number (PAN) or a card verification value (CVV);
- send a request to a real card network or payment rail;
- hold card-present or card-not-present credentials of any kind.

Test data is synthetic. If a real PAN or CVV ever appears in a log, a fixture, or a commit, treat it
as an incident regardless of intent: it is data the platform has no means to protect.

## Trust boundaries

| Boundary | Trust level | Notes |
| --- | --- | --- |
| Internet → gateway | Untrusted | The only component exposed beyond the host's loopback interface. |
| Gateway → services | Authenticated, not confidential | The identity is HMAC-signed and every service verifies it, so a caller cannot assert a role. The connection itself is not mutually authenticated until Phase 15, so a service can still forge an identity if it is reached directly. |
| Service → PostgreSQL | Trusted, isolated per service | Each service holds credentials for its own database only. |
| Service → Kafka | Trusted | No topic-level authorisation is configured. |
| Host developer → local stack | Trusted | The Compose stack binds to `127.0.0.1`; it is a development environment, not a deployment target. |

## Controls in place

### The gateway is the only place a token is read

`GatewaySecurityConfiguration` verifies each token against the realm: `RS256` only, the issuer
matched exactly, `fintech-api` present in `aud`, and expiry checked. The audience is verified rather
than assumed, because the realm issues tokens to other clients and a token minted for one of those
carries an equally valid signature.

Authorisation is then a deny-by-default table over `realm_access.roles`, per path, in
[ADR-0004](decisions/0004-jwt-verified-at-the-gateway.md). A token with a valid signature and the
wrong role receives `403 INSUFFICIENT_ROLE`; a missing, malformed or invalid token receives
`401 AUTHENTICATION_REQUIRED`. Both use the platform's standard error envelope, and neither tells the
caller which part of a forgery to correct.

Only `/actuator/health`, `/actuator/health/**` and `/actuator/prometheus` are served without a token.
Without them a container healthcheck cannot observe the gateway and Prometheus scrapes nothing while
still reporting the target as up, which was measured rather than assumed.

### A service believes an identity only after verifying it

`platform-common-web` registers `InternalIdentityFilter` whenever a non-blank signing key is
configured. The filter verifies an HMAC-SHA256 signature over the subject, username, sorted roles,
correlation id and issue time, rejects anything older than 60 seconds, and only then exposes the
result through `CurrentCaller`. `require()` throws when there is no verified identity rather than
returning a placeholder, so a scheduled job cannot end up acting as a fabricated user.

Two properties are worth stating because they are easy to break by accident:

- **There is no switch to turn verification off.** A service without a key does not trust everybody;
  the filter is not registered and every protected path is `401`. A key that is present but unusable
  fails startup.
- **The gateway strips every `X-Internal-Identity-*` header before adding its own.** A client that
  sends a well-formed header set is not believed, and a header the gateway does not itself write
  cannot survive to a service that reads only one field of it.

`/actuator/health`, `/actuator/info` and `/actuator/prometheus` are exempt, because Docker and
Prometheus cannot present an identity. The exemption is a list rather than a prefix:
`/actuator/env`, `/actuator/heapdump` and `/actuator/loggers` all require a verified identity.

### Secrets never enter the repository or an image

- `.env` is generated by `scripts/bootstrap.sh` with random values, is git-ignored, and is created
  with `0600` permissions.
- `.env.example` contains only `CHANGE_ME` placeholders. `POSTGRES_SUPERUSER_PASSWORD`,
  `SERVICE_DB_PASSWORD` and `REDIS_PASSWORD` have no working default in any committed file.
- Application configuration has **no default for any password**. A service that is not given
  `SERVICE_DB_PASSWORD` fails at startup rather than connecting with a known value.
- `scripts/check-secret-isolation.sh` renders the Compose configuration and asserts that no
  application service receives an infrastructure secret, that no service is handed another
  component's database credentials, and that no two services share a database. It is part of
  `make check`.

### Least-privilege data access

Each service has its own PostgreSQL database and its own role. The bootstrap script grants each role
rights on its own database and nothing else, so a compromised service cannot read another service's
tables. This is verified behaviourally, not just by inspection: a `fintech_cards` session can write
to its own database and is refused access to `fintech_customers`.

The gateway holds no database credentials at all, because it has no database.

### Personal data is unreadable without the master key

customer-service encrypts every personal field with AES-256-GCM under a key derived per customer from
`CUSTOMER_PII_MASTER_KEY`, so a database dump, a backup or a replica is not personal data. The design,
including why the blind indexes are salted differently and why erasure keeps a subject digest, is in
[ADR-0005](decisions/0005-pii-encrypted-at-rest.md).

Three properties are asserted by tests rather than by inspection:

- **One customer cannot read another's row.** A payload only decrypts under the key derived from the
  subject that wrote it, so a mismatched subject is a decryption failure rather than a wrong answer.
- **Interoperability is pinned to a published answer.** The derivation is checked against the RFC 5869
  test vector and against an independently written implementation in the test source. Deriving is the
  one operation where a plausible-looking change silently destroys every stored value, and a test that
  only compared the code against itself would agree with the bug.
- **Erasure is enforced by the data.** `Customer.erase()` nulls the ciphertext and drops the blind
  indexes, and `PiiCipher` refuses to encrypt or decrypt a record with no subject, so a tombstone
  cannot be repopulated by an ordinary write. That the columns are actually null is checked against
  real PostgreSQL, not against a mock.

### Card numbers are not in the database

card-service's `cards` table holds a keyed one-way token, a last four, a brand and a lifecycle. It
has no PAN column, no CVV column, no track data and no PIN column, so there is nowhere to put a card
number even accidentally. The number is minted at issue, shown to the cardholder once and discarded.
The design, and what it costs, is in
[ADR-0006](decisions/0006-card-tokenisation.md).

The property is asserted by test rather than by inspection, because it is the kind of thing that is
true on the day it is written and quietly untrue after a migration:

- **The column list is exact.** `CardPersistenceTest` asserts the `cards` table's columns
  `containsExactlyInAnyOrder`, so a migration that adds an encrypted `pan` column fails the build.
- **The digits are not in the row.** The same test mints a card, casts the row to text and asserts
  the PAN does not appear anywhere in it — which covers a column added under a name the test did not
  think to check.
- **The aggregate cannot hold one.** `Card.issue` takes a `Pan`, reduces it to four digits and drops
  it. There is no accessor, because there is no field.

Two keys are involved and they are not interchangeable. `CARD_TOKENISATION_KEY` is held by
card-service alone and derives values the platform must never invert. `CUSTOMER_PII_MASTER_KEY`
protects values the platform must read back. Sharing one key for both jobs would mean a single leak
does two things and that rotating either rotates both.

A stolen `CARD_TOKENISATION_KEY` does not yield card numbers, because HMAC is one-way. It yields the
ability to test a guessed number against a stored token, which is a narrower capability and is why
this is the key to protect in card-service. It is a base64-encoded 32-byte value with **no default**,
for the same reason the PII key has none: a default tokenisation key would make every token in the
table reproducible by anyone who has read this repository, turning "a database disclosure is not a
card breach" into "a database disclosure plus GitHub is a card breach".

Reads are masked by the service, which is the only layer that knows the owning subject. A masked date
of birth becomes a bare year rather than a fabricated day, and `CustomerControllerTest` asserts a
support caller cannot obtain the unmasked value even though the controller holds it.

### Credentials are per deployment, not per environment file

`SERVICE_DB_PASSWORD` is a single local-development secret shared by the eight database-backed
services. That is a convenience of the local stack, not the intended production shape: in a deployed
environment each service receives its own credential, and the shared local value has no
counterpart.

### Correlation without leaking payloads

Every log line and error response carries a correlation id (`X-Correlation-Id`, propagated by
`CorrelationIdFilter`). The id is generated when absent and is an opaque identifier, so tracing a
request does not require logging the request body.

### Metric labels carry no sensitive values

`ObservabilityAutoConfiguration` adds `application`, `environment` and `version` to every metric. The
values come from configuration; the tag set is fixed, and no request data, identifier, or principal
is ever promoted into a metric label.

### The browser gets an enumerated origin and an in-memory token

The customer UI is static files with no backend, so its controls are browser-shaped: the gateway
answers preflights for exactly one enumerated loopback origin (never a wildcard), the token lives
in memory and dies with the tab (never localStorage, where it would survive for the first XSS
hole), framing is refused outright, and the served files carry no secret — asserted by grep in the
frontend verify script rather than by convention. The password grant the UI uses is fenced to local
development; production moves to Authorization Code with PKCE and disables direct grants on the
realm. See [ADR-0013](decisions/0013-static-customer-ui.md).

## Known gaps

These are absences, not risks that have been mitigated another way.

- **No mutual TLS between the gateway and the services.** Identity headers are signed with a key
  that all nine services hold, so a service that can be reached directly can also mint an identity for
  any user. The signature stops a *client* from asserting a role; it does not stop a *service* from
  doing so. Only the loopback binding and the shared-key distribution make this non-exploitable in
  the local stack. (Phase 15.)
- **One signing key, and it is in `.env`.** Every service holds the same value, so a key rotation is
  a coordinated restart rather than a gateway-only change, and a compromise of any one service
  compromises the ability to forge identity for all of them. (Phase 15.)
- **Role changes are not re-evaluated mid-request.** An identity is accepted for up to 60 seconds
  after the gateway signed it, so a revocation takes up to a minute to take effect and a captured
  request can be replayed inside that window. The bound is a deliberate limit on how long a stale
  authorisation is useful, not a replay defence.
- **No rate limiting.** The gateway has no per-route or per-client limits. (Phase 3.)
- **No encryption in transit inside the Compose network.** Services, Kafka and Redis communicate in
  cleartext on the local network. (Phases 8 and 15.)
- **No Kafka authorisation.** Any client that can reach Kafka can read or write any topic.
- **Flyway runs at application startup.** Acceptable for the local stack and explicitly not the
  production posture, where migrations are applied by a separate job. See
  [deployment.md](deployment.md).
- **Actuator detail is exposed without authentication** on the eight internal services. Only the
  gateway is reachable from outside, but the services should not be published as-is.
- **The PII master key is a single point of total compromise.** It derives a key per customer, so a
  stolen *database* yields nothing readable, but the key itself decrypts everything. It is one
  environment variable in the local stack and a secrets-manager entry in production, and it is the
  value whose loss ends confidentiality platform-wide. Losing it is not recoverable: there is no
  re-encryption path that does not require it. See
  [ADR-0005](decisions/0005-pii-encrypted-at-rest.md).
- **Blind indexes leak equality.** `findByEmailBlindIndex` answers "is this email registered" to
  anyone who can reach the service with the right role. A keyed hash is not reversible, but it is a
  stable identifier for that email, and it is dropped on erasure precisely because it is.
- **No re-encryption job.** The key version travels with each record, so rotation is a deploy rather
  than a table rewrite, but nothing rewrites existing rows afterwards. See
  [architecture.md](architecture.md#added-in-phase-3-and-still-open).
- **No access log for PII reads.** Masking is enforced in the service and tested, but there is no
  record of which support or compliance caller read which profile.
- **The subject digest is joinable across two databases, by design.** `SUBJECT_DIGEST_KEY` is held
  by transaction-service and fraud-service — the only two services that see a subject digest — and a
  purpose-prefixed HMAC under a shared key is a stable identifier. So these two databases can be
  correlated on a subject, and either database plus the key is enough to confirm a *guessed* subject,
  though not to recover one. This is the accepted cost of letting the fraud engine recognise a
  customer across a boundary where the two services share no rows; without it the engine has no
  memory and velocity silently resets. Mitigations: the key is environment-injected and never
  written to disk, `FraudDigestKey` refuses to start without it, and no other service holds it. The
  join is broken deliberately in Phase 15, when mTLS removes the need for services to trust each
  other with an identity. See
  [ADR-0008](decisions/0008-asynchronous-advisory-fraud-scoring.md).
- **Analysts work from digests, not identities.** The fraud queue shows an
  `ownerSubjectDigest`, never a name, email or account. That is the privacy boundary working, and it
  is also an operational limit: an analyst cannot recognise a customer from the queue alone and must
  correlate through Phase 9's reporting path, which will need its own audited join.
- **Fraud can be authorised and then declined later.** Advisory scoring means a payment may succeed
  and a decision arrive afterwards saying it should not have. Every decision records a
  `stepDownRecommended` flag that is *not* enforced. Until it is, the enforcement point is the
  analyst queue, and a missed or unworked alert is a missed control rather than a prevented one.

## Verifying the controls

```bash
make check          # verify, formatting, and the secret-isolation assertions
make check-secrets  # secret and database isolation only
```

The gateway's fail-closed behaviour is covered by
`services/api-gateway/src/test/java/com/fintech/platform/gateway/GatewaySecurityConfigurationTest.java`,
which asserts that health and Prometheus are reachable and that everything else is refused.

Three suites cover the identity path specifically, and each exists because the gap it fills was
observable:

| Test | What it holds in place |
| --- | --- |
| `GatewayAuthorisationTest` | Every role against every path, plus wrong issuer, wrong audience, expiry and malformed tokens. |
| `InternalIdentityForwardingFilterTest` | The exact header set the gateway emits, and that a client-supplied identity never survives. |
| `IdentityContractTest` | Runs the gateway's signer into the service's real verifier, across the module boundary, so a header renamed on one side fails the build. |

`WebAutoConfigurationTest` binds the real property names into the real auto-configuration, which is
the only way to catch a component that starts up and silently trusts its callers. Binding from a
constructed properties object is what let that defect through once already.

Two suites hold the payments path in place, and each exists because the gap was observable rather
than theoretical:

| Test | What it holds in place |
| --- | --- |
| `IdempotencyConcurrencyTest` | Eight concurrent requests on one key make one payment, and the seven that lose the race are told their request is in progress rather than being handed a 500. |
| `TransactionControllerTest` | A replayed response reaches the wire byte-identical, the caller comes from the verified identity rather than the body, and a missing `Idempotency-Key` is a 400 and not a 500. |

Against a running stack:

```bash
TOKEN=$(./scripts/get-token.sh customer)
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/api/accounts                    # 401
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/api/admin/users                                                          # 403
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:9082/actuator/metrics                # 401
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:9082/actuator/prometheus             # 200
```

The payments controls are asserted end to end by `./scripts/verify-payment-lifecycle.sh`, which
provisions its own throwaway identities. It is the only check that can see the two properties above
mattering in production: that `Idempotency-Key` survives the gateway hop, and that a replayed
response is byte-identical to the original. The second is worth stating plainly — the payment is made
exactly once in either case, the status is `201` in either case, and the ledger and the idempotency
table agree in either case, so a status-code assertion passes against a service that is returning a
JSON-quoted string where a client expects an object.

## Reporting

Report a suspected vulnerability privately to the repository owner rather than opening a public
issue. Do not include real card data, credentials, or tokens in a report; describe the exposure and
provide synthetic reproduction steps.
